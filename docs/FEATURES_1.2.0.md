## 一、先说现状：已经有了一半，但用户看不见

`shimeji/engine/petstate.py` 里已经有一套完整的养成数值，而且照搬了 VPet 的
CalMode 公式。但**它自己承认这不是游戏**：

> 数值本身**不是**游戏内容：没有 UI 可以改，也没有游戏目标。它们只是给
> `state()` 提供输入，让行为分布随时间轻轻漂移，避免桌宠每次启动都一模一样。
>
> *The numbers are not a game: there is no UI to change them and no goal to
> chase.*

所以 1.2.0 要做的事，一句话概括：**把「隐形数值」变成「用户能感知的养成」**。

### 已经有的（可直接复用）

| 东西 | 位置 | 状态 |
|---|---|---|
| 4 个数值：心情 / 体力 / 健康 / 好感度 | `PetStatus.__init__` | ✅ 完整，含范围夹取 |
| 状态枚举（生病 / 不佳 / 普通 / 开心） | `PetState` + 中日英名 | ✅ 完整 |
| 15 秒一次的时间漂移（平方根衰减） | `tick_slow()` | ✅ 已在 `manager.py:977` 调用 |

## 二、功能清单（按依赖顺序，建议自上而下做）

### F1 · 状态面板 —— 看得全 ✅ 已完成（2026-10-31）

**成本**：低　**用户感知**：中　**依赖**：无（可先做）

⚠️ **不是从零开始**：托盘面板 `taskbar_panel.py:326` **已经在显示一行状态**
（`开心 心情 80 体力 90`）。缺的是：

- **健康和好感度没显示** —— `summary()` 只返回状态名 + mood + energy
- **多角色时只有第一只当「代表」** —— 面板 320px 宽，原注释写明「塞不下 4 行数值」
- 刷新频率 500ms，够用

所以这一项是**扩展**而非新建：

- 把 `summary()` 补全成四个数值（或给它加一个 `detail()` 变体，保持单行摘要给面板用）
- 多角色：面板里放不下就做成悬停/点开的**弹出层**，而不是砍掉信息
- 复用 `PetStatus.summary(lang)` 与 `STATE_NAMES_ZH/EN`（都已存在）

**验收**：能看到心情 / 体力 / 健康 / 好感度**四个**数值；多角色时能看到每只的
状态（而不是只有第一只）；拖拽宠物后数值会变。

**为什么先做它**：其余功能都要靠数值可见才能被感知。这是**前提**。
注意它比原以为的省力 —— 面板和 `summary()` 都现成，只是信息不全。

#### 实际做出来的（2026-10-31）

- `PetStatus.detail()` —— 四个数值 + 状态名的**结构化**返回（不是拼好的字符串，
  面板要自己排版、要列多只）
- `PetStatus.state_name(state)` —— 状态名走 i18n（新增 `state.*` 三语键）
- 新文件 `shimeji/gui/status_window.py` —— 每只宠物一块：名字 + 状态 +
  四条数值进度条，1 秒刷新一次
- 面板的 `state_label`(QLabel) -> `status_btn`(扁平 QPushButton)，点开详细窗口；
  面板仍保持 320px、摘要仍是单行，完整数值放进弹出层

⭐ **顺手修了一个真实的 i18n bug**：`summary()` 以前是硬编码的
`if lang.startswith("en") ... else 中文`，而 `ja_JP` 不以 "en" 开头 ——
**日语用户看到的是中文的「心情 / 体力」**。现在三语都正确
（`普通 気分 50 体力 70`）。

⭐ **`panel.mood` / `panel.stamina` 这两个键三语早就存在，却全项目无调用** ——
它们就是为这里准备的，这次接上了。

测试：`analysis/verify_status_panel.py`（27 项）。变异测试确认鉴别力：
退回硬编码 summary -> 3 项失败；`detail()` 砍掉两个数值 -> 3 项失败。

### F2 · 互动细分 —— 摸得着 ✅ 已完成（2026-10-31）

**成本**：低　**用户感知**：高　**依赖**：F1（否则看不出区别）

补上 `interact()` 里那行明写的待办：

```python
del kind  # 强度差异留到 1.1.0 有了养成 UI 再细分
```

按 `kind` 区分强度：

| 互动 | 心情 | 好感 | 体力 | 理由 |
|---|---|---|---|---|
| 摸头 / 点击 | +多 | +少 | 几乎不耗 | 最轻量、最高频的互动，应该是主要的正向来源 |
| 拖拽 | +少 | +多 | -中 | 用户在"带着它走"，亲密但费劲 |
| 抛出 | +多 | +少 | -多 | 玩闹，开心但最累 |

⚠️ **最重要的一条**：现在**点击/摸头完全不算互动**。用户点宠物是最自然的动作，
却得不到任何回应 —— 这是"感觉不到养成"最直接的来源。

**验收**：摸头后心情涨、体力几乎不变；抛出后心情涨更多但体力明显下降；
三种互动的数值变化各不相同（不是都走同一条公式）。

#### 实际做出来的（2026-10-31）

`PetStatus.interact(kind)` 真的按 `kind` 给不同数值了（函数体里那行
`del kind` 的待办已删）：

| kind | 心情 | 好感 | 体力 | 思路 |
|---|---|---|---|---|
| `pat` 摸头 | **+2.2** | +0.15 | **-0.2** | 最轻量也最高频，主要的正向来源 |
| `drag` 拖拽 | +0.8 | **+0.45** | -1.6 | 用户在「带着它走」，亲密但费劲 |
| `throw` 抛出 | +1.8 | +0.10 | **-2.4** | 玩闹，开心但最累 |

量级参照 `tick_slow()`（心情每 15 秒 -0.6）：摸头 +2.2 约等于抵消 55 秒的
自然衰减 —— 摸几下就看得见变化，但不会几下就满。

**怎么区分「摸头」和「拖拽」**：按下时记锚点，松开时看**位移** —— 位移 < 8px
算摸头，否则算拖拽（+ 抛出）。阈值 8px 是为了让手抖、点歪都不算拖拽。

⚠️ **不改产品行为**：宠物**照样**会在松手时被「抛出」（`_force_behavior(BEHAVIOR_THROWN)`
原样保留）。F2 只改**数值按哪种互动结算**。

⭐ **顺带发现**：以前按下即 drag、松开即 throw，所以**点一下宠物走的是
drag + throw 两次结算**。现在点一下只算摸头。

测试：`analysis/verify_interaction.py`（17 项）。三个变异全部被抓到：
- `interact` 不区分 kind -> 11 项失败
- 删掉松手后的抛出行为 -> 1 项失败
- 摸头阈值失效 -> 2 项失败

⚠️ **改了一条既有断言**：`verify_physics_101.py` 的「拖拽宠物会涨心情」原本
在 `begin_drag()` 之后立刻检查，而数值现在在**松手时**结算。已补上
`end_drag()`，并真的移动锚点让断言名副其实（措辞是「拖拽宠物」）。

### F3 · 状态台词 —— 有反馈 ✅ 已完成（2026-11-02）

**成本**：中　**用户感知**：中　**依赖**：F1、F2

现在 `serifu.py` 只在行为名带「セリフ」等词时冒泡。加上**按状态触发**：

- 状态变化时说一句话（生病时抱怨、开心时撒欢）
- 好感度跨过里程碑时说话（第一次到 50、第一次到 100）
- ⚠️ 必须**节流**：状态频繁变化时不能每帧冒泡，否则变成噪音
  （气泡基建见 `gui/balloon.py`，台词见 `serifu.py`）

**验收**：把宠物"养成"到开心状态会看到不同的话；同一状态短时间内不会重复刷屏。

#### 实际做出来的（2026-11-02）

**两条触发线**：
- **状态迁移**：`PetStatus.cached_state()` 检测到状态真的变了 -> 通知
  `on_state_changed(new, old, owner)` -> Manager 说一句对应状态的话
- **好感里程碑**：好感跨过 **50 / 80 / 100** 时各说一句，**每个一生一次**
  （50：「我们更熟了一点呢」/ 80：「最喜欢你了！」/ 100：「一直陪着我吧」）

**台词来源沿用「角色自带 > 全局 > 内置」**：角色包可放
`conf/serifu_<state>.txt` 整体替换某一组；设置可配 `serifu_state_<state>`；
都没有时用内置的四组三语台词（生病/不佳/普通/开心各 3 句）。

**职责边界**：`PetStatus` **不 import Qt、不知道台词**，只通知回调（可测试）；
Manager 负责节流、挑台词、`say()`。

测试：`analysis/verify_state_lines.py`（14 项，**不弹窗口** —— 把 `Manager.say`
换成记录器，只断言「该说时说了、不该说时没说」）。三个变异全部被抓到：
- 去掉节流 -> 「冷却期内不说」失败
- 里程碑改成可重复 -> 「一生一次」失败
- 删掉状态回调 -> 「状态变化说一句」2 项失败

⭐⭐ **这次踩的坑（值得记）**：第一版 Manager 用
`next(x for x in pets if x.status.on_state_changed is self._on_...)`
反查触发宠物。但**每次访问 bound method 都会新建一个对象**，两个用 `is`
比较必然 False —— 结果一条状态台词都说不出来。修法：`PetStatus` 加 `owner`，
回调把宠物直接带进来。**判断「这是不是我的方法」要用 owner，不要 `is` 比较
bound method。**

**用户可配置**：`serifu_state_cooldown`（秒，默认 30；设为 0 = 状态台词整个
关掉）。

## 四、建议的顺序与理由

```
F1 状态面板 ──► F2 互动细分 ──► F3 状态台词 ──► F4 番茄钟联动
                                                      │
F5 多显示器配置（独立，可插队）                        │
F6 编辑器增强（独立，可插队）
```

**为什么 F1 必须最先**：其余四项都要靠面板才能被感知。先做面板，
后面的每一步用户都立刻看得见；反过来做，做成三个功能用户也只觉得"没变化"。

**为什么 F2 紧随其后**：它补的是最明显的一个洞 ——
**现在点击/摸头完全不算互动**。成本极低（只改 `interact()` 一个函数体 +
加一个调用点），但它是"感觉像在养宠物"的关键。

**F5 / F6 可插队**：与主线无依赖，任何时候都能做。

## 五、贯穿始终的一条约束

这些功能**都不能破坏引擎层的核心性质**：

> 状态只改行为出现的**频率**，绝不改**行为集合本身**。

（`PetStatus.weight_bias()` 的设计就是这个原则，`brain.py` 也在遵守。）

所以：好感度低的时候宠物**不会消失、不会拒绝互动**，只是发呆多、跳跃少。
**数值是调味，不是门禁** —— 做成"不理它就惩罚用户"就背离了桌宠的定位。

已有测试 `verify_physics_101.py` 的「1.0.3 CalMode：状态只改频率，不改动作」
一节在守这条，新功能**不能让它挂**。

## 六、每个功能做完的通用验收

沿用项目现有的纪律：

1. **新断言在旧代码下会挂**（`git stash push -- <源码>` 验证）
2. **用变异测试确认断言有鉴别力**（故意改坏源码，确认它会挂）
3. **测试不能依赖「用户当时在干什么」** —— 需要注入接缝
   （⚠️ 特别注意：`Environment.refresh()` 每 tick 把光标重置成**真实鼠标**，
   涉及光标的测试要**每帧重设**）
4. 跑完整回归（18 项）确认无副作用
